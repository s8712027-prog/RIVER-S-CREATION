# 商用落地藍圖

## 產品定位

Curve OS Guard 是「製程判讀與追溯助手」，不是閉迴路自動控制器。它先向操作／製程人員呈現可驗證的證據，再由受授權的人員依既有 SOP 作出設定調整。

本文件的目標架構不等同於目前原型的既有能力。v2.0 目前可離線評估單一 CSV、產生報告與本機 HMI；客戶資料接入與 Shadow Mode 的能力邊界請以 [DOCUMENTATION_AUDIT.md](DOCUMENTATION_AUDIT.md) 為準。

## 分階段導入

| 階段 | 目標 | 客戶提供 | 可驗收成果 |
|---|---|---|---|
| 0. 資料盤點（1–2 週） | 確認資料可用性與責任歸屬 | historian schema、配方、檢驗欄位 | 資料契約與欄位映射簽核 |
| 1. Shadow Mode（4–6 週） | 不干預生產地評估規則與資料品質 | 連續歷史／即時資料 | 每卷可追溯報告、異常清單、人工覆核差異 |
| 2. Case Intelligence（6–10 週） | 建立可信的相似案例與結果回測 | 已標註的最終品質結果 | precision／recall、查找時間改善、風險校準報告 |
| 3. Advisory（依治理核准） | 對已驗證模式提出受約束建議 | SOP、角色與簽核流程 | 建議採納率、稽核軌跡、無自動下發控制 |

## 部署參考架構

```text
OT Historian / MES / LIMS
          │（唯讀、可稽核資料交換）
          ▼
Edge Connector ──► Curve OS Guard Engine ──► 本地報告 / HMI
                         │       │
                         │       ├── Rules Catalog（版本與簽核）
                         │       └── Audit Log（輸入雜湊、模型、操作者）
                         ▼
          Parquet 原始曲線 + Metadata DB + 受控向量索引
```

系統在 Shadow Mode 必須維持唯讀；與 PLC/DCS 的寫入連線不在本產品初始範圍內。

## PoC 升級為 Shadow Mode 的必做門檻

1. 以 recipe event、L2 狀態或經簽核的 zone 邏輯取代目前的等分三段示範分段。
2. 將逐點 `setpoint_c`、鋼種、厚度、爐區／感測器 ID 與不可變 `coil_id` 納入資料映射；不可只依 CSV 檔名。
3. 建立受審核的歷史資料寫入流程。評估報告不能直接視為可用歷史案例。
4. 將配方版本、簽核紀錄、操作者／服務帳號及來源時區寫入稽核軌跡。
5. 在有最終品質標籤之前，將所有案例結果固定為 `NOT_CALIBRATED`；禁止採用任何未回測的 failure probability。

## 治理與驗收

1. 每份輸入保存來源、時區、資料雜湊、評估時間、配方版本與規則版本。
2. 每項建議均要提供觸發證據、嚴重度與安全措辭，禁止未經簽核的自動 setpoint 調整。
3. 預測失敗風險必須有時間上正確的 train/test 切分、最小證據數、置信區間與 drift 監控。
4. 將「曲線資料品質」和「成品品質」分開治理；前者不及格時只能要求補資料，不能推論後者。
5. 上線 KPI 應至少有：追查時間、人工覆核一致率、提前辨識率、誤報率，以及被避免的不良成本；不以單一模型準確率取代業務價值。

## 客戶工作坊的三個決策

- 哪些鋼種／配方先納入？初期應選資料完整、規格穩定且不良成本明確的一個 family。
- 何者是最終品質標籤？檢驗值、客訴、不良代碼與報廢必須有優先順序與可追溯定義。
- 操作建議由誰覆核？每一類告警應指定製程、品質或設備責任人及回填處置結果。
